# Abstract

C++ has vocabulary types and computational contexts that are individually well
understood, but it lacks a uniform way to traverse a structure while producing
contextual results and then *transpose* the result into a single outer context.
This problem appears today in combinations such as containers of `optional`s,
containers of senders, and lanewise or zipped structured computation.

This paper proposes a shape-preserving traversal facility together with
`transpose` operations that convert a structure of contextual values into a
contextual structure. The proposal is based on *independent contextual
composition* rather than on general sequential dependence.

The paper also proposes a bundled customization model. That mechanism is
included because current trait-only and per-operation customization techniques
are not strong enough to bundle applicative primitives and derived operations
coherently.

# Before / After

The operation flips `structure<context<T>>` into `context<structure<T>>`,
preserving shape.

::: cmptable

### Before

```cpp
std::vector<std::optional<int>> in = ...;
std::optional<std::vector<int>> out{std::vector<int>{}};
for (auto& o : in) {
    if (!o) { out.reset(); break; }
    out->push_back(*o);
}
```

### After

```cpp
auto out = beman::transpose::transpose(in);
// out : std::optional<std::vector<int>>
```

:::

The same verbs serve a deferred (sender-like) context and a lanewise (SIMD/zip)
context with no per-domain wording:

```cpp
beman::transpose::transpose(vector_of_senders);  // -> sender<vector<T>>
beman::transpose::transpose(vector_of_ziplists); // -> zip_list<vector<T>>
```

# Proposed operations

- `traverse(f, structure)` — apply an effect-producing `f` to each element and
  transpose the effects, preserving shape.
- `transpose(structure)` — `traverse` with the identity function.
- lifted contextual application: `invoke` — a plain function over N in-context
  arguments, McBride & Paterson's canonical form `pure f ⊛ u1 ⊛ … ⊛ un`. It
  is the user-facing application verb. Instances opt in through either
  basis — `pure` + `invoke`, or `pure` + `ap` (the classic one-step
  application) — and the implementation derives the missing one (GHC:
  `MINIMAL pure, ((<*>) | liftA2)`); see
  [`ap` as basis, `invoke` as interface](#ap-as-basis-invoke-as-interface).

Each is proposed as an object, so that a call site can name the operation and
let the instance be deduced from the argument that keys it; see
[Operation objects and the lookup modes](#operation-objects-and-the-lookup-modes).

# `ap` as basis, `invoke` as interface

The classic applicative-application spelling — `ap(cf, cx)`, a callable held
*inside* the context, applied to one argument-in-context at a time — is a
perfectly good **basis** for Applicative, and the design supports it as one:
an instance may opt in with `pure` + `ap` when one-step application is its
natural formulation (the reference implementation's shape-aware binary tree
is exactly such a case), and the n-ary `invoke` is derived.

What `ap` is not is the **interface**. Chains of one-step applications are
an artifact of Haskell's currying: `f <$> u1 <*> u2 <*> u3` works there
because partial application re-inserts a function into the functor at every
step. C++ is not curried; that cost is real, and the design confines it to
the derivation direction — call sites never see it.

The decisive argument for the interface choice is in this paper's own
motivation: `std::simd::vec` holds only vectorizable scalars, so
`vec<callable>` **is not a type** and `ap` cannot be spelled for it even in
principle — while the n-ary `invoke` (the lane-wise generator) is exactly
what the hardware operation is. An `ap`-shaped interface would lock out one
of the three motivating domains; `invoke` serves all three, and `ap`
remains available as a secondary operation exactly where the context can
hold a callable (the constraint vanishes cleanly where it cannot).

Accordingly, the law suite is stated in `invoke` form (identity,
homomorphism generalized to the n-ary core, interchange as floating a
`pure` operand out of an application, functor composition), with basis
coherence — a native `ap` agreeing with the derived one, and vice versa —
checked per instance.

# Operation objects and the lookup modes

The operations should be objects, so that a call site can name the operation
and say nothing about the instance.

These objects are not customization points, and the distinction carries the
argument of [Why a bundled customization
mechanism](#why-a-bundled-customization-mechanism). Customization happens in
one place, at `applicative_typeclass<T>` and its siblings, where an instance
opts in to the whole bundle at once. An operation object performs that lookup
and calls into the bundle. There is no per-operation hook, no ADL path into
the operation, and nothing an instance author can specialize that would make
`invoke` mean something other than the instance's own `invoke`. The name
"customization point object" is therefore misleading for these, however
familiar it has become: they are the reverse, a fixed spelling over a
customizable bundle.

With them, an instance can be reached four ways, in decreasing order of what
the call site says:

1. Implicit lookup through the variable template, then a member call:
   `applicative_typeclass<T>.invoke(f, ax)`.
2. An instance passed as an ordinary argument, for algorithms that take one.
3. NTTP pinning, where an enclosing template carries `const auto& TC =
   applicative_typeclass<CONTEXT>` and fixes the instance at instantiation.
4. The operation object: `invoke(f, ax)`.

Modes 1 through 3 all name the instance first. Mode 4 is for the calls where
the instance is not the interesting part of the call, and for the case where
the earlier modes are unavailable: a non-template function has no template
parameter list, so it can not carry mode 3 at all, and before mode 4 such a
function had either to open with a block of lookup declarations or to become a
template for no reason of its own.

There is a cost, and it should be stated where LEWG will see it. An object
takes no explicit template arguments, so mode 3 is not available *on the
object*: the pinning parameter has to move from the call operator to the
object's own type, which is a second name (`invoke_with<TC>(f, ax)`). Modes 1
and 2 remain untouched, and reaching an alternate instance through them is
unchanged.

`pure` is the exception in both directions. It builds a context instead of
consuming one, so no argument keys the lookup and the context must be named:
`pure<C>(value)`. That form is a template of objects, which means its instance
pinning is an ordinary template argument and needs no second name.

Call LEWG's attention to the naming question this opens. Every operation given
an object also claims a name at namespace scope, and the derived operations of
the fold family — `length`, `empty`, `to_vector` — are generic enough to
collide with existing standard names. The reference implementation ships them
so that the collision is visible; the proposed set should be settled by naming
review.

# Why not Monad

Monad is deferred, not rejected — absent because nothing proposed needs it,
not because it is unwanted.

Everything about the typeclass-object design points toward a Monad instance
eventually. A consistent generic name for sequential composition is exactly
the kind of thing the mechanism exists to provide: today's spellings —
`optional::and_then`/`or_else`/`transform` ([@P0798R8], C++23), the same
family on `expected` ([@P2505R5]), `let_value` on senders — are per-type
member functions, so no algorithm can be written once, generically, over
anything sequentially composable. That is the gap typeclasses close, and the
reference implementation's `monad.hpp` — `bind`, `join`, Kleisli
composition, an `optional` instance, `invoke` synthesized from `bind` +
`pure` — demonstrates the mechanism carries Monad without strain.

It is omitted from this paper for one reason: no operation proposed here
calls `bind`. `traverse` and `transpose` require Applicative — independent
contextual composition — and the three motivating domains work precisely
because no operand's context depends on another operand's value. Proposing
Monad in R0 would attach the family's largest naming-and-teaching
discussion to a paper whose operations never use it.

When a proposal needs to be generic over sequential composition, Monad is
the paper to write; the coordinated set leaves that slot open, and the
evidence that it slots in cleanly is already in the tree. For now.

# Non-goals for R0

- Standardizing the full algebraic hierarchy.
- A Monad abstraction, in this paper or the coordinated set (see
  [Why not Monad](#why-not-monad)).
- Proposing `ap` as the user-facing application verb: it is a supported
  instance basis and a secondary operation, never the interface (see
  [`ap` as basis, `invoke` as interface](#ap-as-basis-invoke-as-interface)).
- A Foldable abstraction: the fold family's motivation is structures that
  are not ranges, and it is proposed by the recursive-tree-algorithms
  companion paper. The reference implementation's `fold.hpp` and
  `monad.hpp` are evidence that the mechanism scales, not proposed wording.
- Solving every naming question for adjacent abstraction families.
- Turning the paper into a generic customization-framework survey.
- Making tree containers carry the motivation for the paper.
